# 经验总结 —— 顶栏悬停明细「在 Edge 上不显示」的排查与修复

> 日期：2026-09-27　·　现象：v4.1 上线的顶栏资源悬停明细，用户在 Edge 里悬停「金钱」无任何反应。
> 结论先行：**不是 Edge 的兼容性问题，是代码真的有 bug** —— 只是它只在真浏览器里才会暴露。

---

## 一、排查过程（值得复用的路径）

1. **不猜，先复现。** 用真浏览器（browser-use 驱动 Chromium，与 Edge 同核）注册测试号 →
   进入游戏 → 给 `window` 挂 `error` / `unhandledrejection` 收集器 → 对
   `[data-res="money"]` 派发 `mouseover` → 读 `#res-tip` 的 classList 与 innerHTML。
2. 一次就抓到现场：

   ```
   Uncaught TypeError: p.companyUpkeep.neg is not a function @ res-tip.js?v=4:117
   tipHidden: true, tipHtmlLen: 0
   ```

3. 根因：`res-tip.js` 的金钱明细里写了 `p.companyUpkeep.neg()`，而**项目的自研
   `shared/decimal.js` 根本没有 `neg()` 方法**（只有 `isNeg/cmp/add/sub/mul/div/pow…`，
   全代码库对负号的惯例写法是 `isNeg() ? '' : '+'`，从来没有 `.neg()`）。
   构建器在拼 HTML 的第一步就抛 TypeError，`showTip` 永远走不到
   `classList.remove('hidden')` —— 面板静止不动，且控制台之外没有任何可见征兆。

## 二、为什么三层验证都没拦住它

| 关卡 | 为什么漏过 |
|---|---|
| 4067 项测试 | core/frontend/e2e 都不触及 res-tip 的构建器（UI 新功能） |
| Node DOM 桩冒烟 | 口径函数（moneyIncomeParts / qiRateParts）验证过，但**桩无法触发 hover，构建器的 HTML 拼装分支从未被执行** |
| 代码审查 | `.neg()` 语法完全合法，node --check 通过；错误是「API 契约」层面的，不是语法层面 |

**教训：纯逻辑可以桩测，「拼装展示层」的分支桩测不到 —— UI 新功能的最终关口必须是
一次真浏览器回归（挂错误收集器 + 触发事件 + 读渲染结果），成本只有一分钟。**

## 三、修复（三件套）

1. **代码**：`rate()` 旁边新增 `costRate()`（负号显式加，零值回 `+0`），不再调用不存在的 `.neg()`。
2. **测试钉死**（tests/frontend.test.js 新增「Decimal API 契约」小节，+17 条）：
   - 反向断言：app 源码禁止出现 decimal.js 未实现的链式方法
     （`.neg( .abs( .ceil( .floor( .round( .sqrt( .log( .ln( .recip(` ——
     正则带 `(?<!Math)` 排除 `Math.round` 这类静态调用；core 里实现了的方法自动放行）；
   - 正向断言：`isNeg/cmp/gt/gte/lt/lte/add/sub/mul/div/pow` 必须存在 ——
     前端广泛依赖它们，谁删谁破坏性变更。
3. **顺带排掉的第二个雷：缓存戳**。index.html 的 `?v=4` 从第二轮优化起就没再手动
   bump 过（这个手工纪律历史上已失败两次），用户端很可能同时跑着缓存的旧
   game-core/app 脚本 —— 排查时它是头号嫌疑。现已改为**服务端启动时自动注入**：
   - `server/index.js` 启动时读入 index.html，把所有 `?v=<数字>` 统一替换为
     `?v=<启动时间戳>`（base36），`/` 路由显式 `Cache-Control: no-cache`；
   - 每次重启服务端，所有脚本 URL 必然变化，浏览器必然重新拉取；
   - 以后改代码**不再需要记得 bump 版本号**。

## 四、沉淀成纪律

1. **调用 shared 层 API 前先看方法面**：自研库不是 lodash，方法以
   `shared/decimal.js` 的实测为准；不确定就先 `grep prototype`。测试已把
   「禁止未实现方法」钉成反向断言，再犯会在 `npm test` 当场爆。
2. **UI 新功能交付前过一遍真浏览器**：Node 桩验证逻辑，真浏览器验证「真的能看见」。
   本项目的 `tools/browser-check.py` 与 browser-use 驱动都可做；关键动作是
   **挂全局错误收集器再触发事件**——很多 UI bug 的唯一症状就是一条被吞的 console error。
3. **任何「手动纪律」只要失败过两次，就改成自动化**：缓存戳如此，
   以后再遇到「记得做 X」类的约定，直接上代码化保障。
