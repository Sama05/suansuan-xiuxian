## 一、项目概况

## 二、架构分析

### 2.1 总体分层

```
浏览器                                   服务端
┌─────────────────────┐                ┌──────────────────────────┐
│ index.html (八页)    │                │ server/index.js          │
│ app.js               │  HTTP/JSON     │  ├ /api/register|login   │
│  ├ 100ms tick        │ ────────────▶ │  ├ /api/load  离线结算    │
│  ├ 渲染(值缓存+签名)  │ ◀──────────── │  ├ /api/save  防作弊合并  │
│  └ 事件栏(差值观察)   │  state/config  │  ├ /api/action 服务端权威 │
└─────────┬───────────┘                │  └ /api/view  实时视图    │
          │ 调用                        └───────────┬──────────────┘
          ▼                                        ▼
┌──────────────────────────────────────────────────────────┐
│ shared/game-core.js —— 同一份 tick，两端各跑一份           │
│   createState / hydrate / serialize / tick / 全系统逻辑    │
│ shared/game-config.js —— 唯一数值来源；decimal.js 大数     │
└──────────────────────────────────────────────────────────┘
                       ▼
              server/db.js → SQLite(data/game.db, WAL)
```

**这是本项目最核心的一个架构决策：前后端共用同一份 `tick()`。**
前端每 100ms 推进实时手感，服务端在 `/api/load` 用同一函数做离线结算。两端结果
逐位一致的前提由两条纪律保证：

1. **一切随机必须确定性化** —— 行情价 `goodsPriceFactor`、股价 `stockFactor`、
   渡劫结果 `tribulationRoll` 全部是「状态的纯函数」（散列/超越函数，无
   `Math.random()`）。
2. **一切时间必须分清口径** —— 四条时间线（游戏内时间 / playTime 行情时钟 /
   现实秒 dt / 精力）在 `stepTick` 里严格分段，注释反复强调「改逻辑不要打乱顺序」。

### 2.2 服务端权威与防作弊（分层防御）

| 层 | 手段 |
|---|---|
| hydrate | 全字段夹取（段位/层数/道行/持仓/期数游标不许越界或超前） |
| /api/save | 只增不减清单（realm/totalJobs/devices/learned/company/rebirth/tribulation…）+ `founded` 单向门 + 兵解 409 拒收 |
| /api/action | 高风险操作服务端重算（渡劫/兵解/买加成/股市成交），客户端只提交意图 |
| 语义层 | 库存裁到仓库容量、股数夹到流通盘、渡劫走服务端避免「只增保护复活资产」 |

防作弊边界在 README 里如实声明（money / pressure / shares 属「可夹不可验」类），
这是诚实的取舍而非疏漏。

### 2.3 性能设计（有实测数据支撑）

- 行业传导递归：显式传行业指数 + 剩余层数预算 + 按 (行业, 层数) 记忆化，
  337ms → 31ms（v3.2 结论，代码注释里完整保留）。
- 股市报价：`stockBuyQuoteWith` 把不变量提出二分查找，31ms → 4.7ms。
- 渲染：`setText` 值缓存、列表签名重建（`data-usig` 跟随元素而非模块级 Map）、
  SVG 按 (标的, 期, 冲击) 缓存、顶栏 grid 固定列宽防抖。

### 2.4 测试与工程化

- 4067 项测试覆盖三层：核心数值（2944）、前端结构+渲染值（529）、接口 e2e（507）。
- 反向断言钉住历史坑（`.res-group` 禁止 flex-wrap、折叠不得重建 DOM、
  `autoTier === false`、渡劫失败样本、兵解 409）。
- 工程细节到位：原生模块 ABI 修复脚本、端口占用友好报错、WAL checkpoint、
  SIGINT/SIGTERM 优雅退出、unhandledRejection 响亮失败。

### 2.5 架构总评

**优点**：单一事实来源（config / core / 存档）贯彻得很彻底；确定性约束贯穿
全部跨端逻辑；注释记录「为什么」与踩坑史，是罕见的可维护性资产；测试与文档
密度在同类项目里属于上游水平。

**短板**：
1. `game-core.js`（5000 行）与 `app.js`（4100 行）是两个超大 IIFE，模块内无子分区
   导出，靠注释分节 —— 定位靠搜索，圈复杂度集中在 stepTick 与两个 renderPage。
2. 服务端 `/api/action` 的分发是巨型 switch（本次已收敛样板，但结果映射仍逐 case 手写）。
3. 前端渲染是「全量函数 + 手动差分」，没有虚拟 DOM；靠纪律而非框架保证不漏更新。
4. 部分工具脚本会随 app.js 演进漂移（本次实测：`tools/chart-preview.js` 已断，
   详见 §4）。

## 三、本次冗余优化（已全部落地并验证）

原则：**只做行为等价的重构**。改前先 grep 测试断言（如 `core.test.js:41` 钉住
`autoTier === false`），改后全量测试 + 自检 + 图表预览三重验证。

### 3.1 server/index.js（1191 → 1146 行）

| 冗余 | 处理 |
|---|---|
| `/api/action` 19 个 case 各抄一份「失败→存档→400+回传state」样板，且每份 serialize 两遍 | 收敛为 `rejectAction(res, s, userId, msg)`，serialize 只跑一次，行为等价（约 -95 行） |
| `buyDevice` case 里 `result` 的失败分支是死代码 | 删除，先判失败再组成功结果 |

### 3.2 public/js/app.js（4197 → 4104 行）

| 冗余 | 处理 |
|---|---|
| `priceChartSVG` / `stockChartSVG` 约 165 行逐行同构（仅期数入口 / 自然价来源 / aria 标签三处不同），改一处忘另一处即两条图对不上 | 合并为 `lineChartSVG(o)` 统一实现，两个原函数变成 10 行薄封装（产线：走势 SVG 由同一函数产出） |
| `rebirthAction` / `companyAction` / `stockAction` 三份逐字相同的 `/api/action` 通道 | 合并为单一 `serverAction`，14 个调用点全部改走它（约 -70 行） |
| kind 判定三元式在 4 处重复 | 提取 `kindTag(kind)`，`marketKindOf` 与股票行共用 |
| `new (window.Decimal || Object)(0)`（兜底类型根本不可能走到，真走到反而是 bug） | 统一 `new D(0)` |
| `fmt(new D(D.fromJSON(x)))` 双重包装 | `fmt(D.fromJSON(x))`（fmt 自带 fromJSON） |

### 3.3 shared/game-core.js（5035 → 5014 行）

| 冗余 | 处理 |
|---|---|
| `createState` 里 `autoTier` 在对象字面量中定义两次（`true` 后被 `false` 覆盖，属「隐性 winner」写法） | 只保留生效的 `false` 并注明废弃背景（测试钉住此值，行为不变） |
| 7 处「孤儿 JSDoc」堆在错误函数头上（如 `gameSecondsPerRealSecond` 的说明挂在 `energyRegen` 上、`realComputeOf` 的说明三连堆在 `computeBreakdown` 上），误导读者 | 全部归位到正确函数或删除过期版本 |
| `industryPriceIndexAt` / `industryCostIndexAt` 两条传导递归逐行相同（仅 pricePass/passThrough 与缓存前缀 `I|`/`C|` 之差） | 合并为 `industryPassIndexAt(s, id, rem, passKey, tag)`；缓存 key 逐位不变，记忆化行为不变 |
| `goodsWindow` / `goodsWindowWith` / `stockWindow` 三份相同的窗口范围计算 | 提取 `windowRange(cur, past, future)`（含「开局单期向后补一期」的边界语义） |
| `tribulationReady` 函数体挤在 `{` 同行 | 规范换行 |

### 3.4 刻意不改的「疑似冗余」

- `db.js` 的 register/login 同步/异步成对：注释已说明是给离线脚本的刻意设计。
- `/api/save` 与 hydrate 里重复的夹取：属于纵深防御（两层挡不同攻击面），非冗余。
- `rushJob` 与 `advanceWork` 的结算循环有细微差异（催工清进度、进度守卫不同），
  合并风险大于收益，保留。

## 四、顺手修复：tools/chart-preview.js（基线即损坏，非本次引入）

**症状**：`node tools/chart-preview.js` 在未修改的 HEAD 上即报
`Cannot read properties of undefined (reading 'innerHTML')`（已用 `git stash`
对照验证）。

**根因 ×2**（工具随 app.js 演进漂移）：
1. 其 DOM 桩的 `mkEl` 缺 `getAttribute/setAttribute`（注释自称与
   frontend.test.js 同源，但漏了这段）—— v3.8 的 `renderLineUnits` 读
   `data-usig` 重建签名时抛 TypeError，`renderAll` 整链中断，市场页永不渲染。
2. 预览存档没买设备、没拨「工业产能」份额 → 实际算力 0 → 全厂停产 →
   「库存 0 件」，即使渲染成功也没有数据可画。

**修复**：桩补齐属性方法（与 frontend.test.js 对齐）；存档补两台设备 +
`s.alloc.industry = 0.5`。修复后成功导出 `preview/company-chart.html`
（库存 500 件、288 条迷你走势、大图 SVG 无 NaN、抛压自然价参考线正常）。
这也顺带验证了本次 `lineChartSVG` 合并的正确性。

## 六、建议（按优先级，均为后续可选项）

1. **拆分超大文件**：`game-core.js` 按系统切成 `core/state.js`、`core/market.js`、
   `core/stock.js`、`core/company.js` 等模块（保持单一 `module.exports` 聚合出口，
   前端加载顺序不变）；`app.js` 同理按页拆分。当前靠注释分节，重构窗口宜趁测试
   完备时做。
2. **`/api/action` 表驱动**：把 19 个 case 的「核心函数 + 结果映射」压成一张
   `{ action: { run, pack } }` 表，进一步消除 switch 的重复形状（本次已把失败路径
   收敛，成功路径的 `.toJSON()` 映射仍逐 case 手写）。
3. **工具防漂移**：chart-preview 与 frontend.test.js 的 DOM 桩是复制关系，已第二次
   出现不同步。抽成 `tools/_dom-stub.js` 单一来源，两边 require。
4. **补充跨页回归**：前端渲染值测试集中在公司/市场/股市页，境界/工作/投向页的
   「渲染值」断言较少，改 renderTop 一类公共函数时主要靠人工核对。
5. README 提到的两项数值复核（转生衰减对照、股市波动率曲线）仍开放，属于数值层
   而非代码层。
