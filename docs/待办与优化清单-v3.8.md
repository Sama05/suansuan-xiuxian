## 二、尚未完成的功能

### 1. 最高境界之后没有新内容
- 境界只有 8 阶，第 8 阶「合体」即封顶（`GAME.realms.length = 8`）。飞升 / 更高境界未实装。
- 到顶后唯一的长期玩法是**兵解转生**（该存档已转生 2 次、累计道行 260）。
- 但转生的核心收益是「设备算力上限」（当前 3.16e8）和道行折扣，而后期实际算力已经是 **7.2e19（有效设备算力）/ 4.8e23（含加成）** 量级 —— 转生带来的提升相对后期盘面约等于噪声，**缺少「转生后明显更强」的正反馈**。

### 2. 淬体层数在最高境界无法继续增长
- 淬体层数只在**渡劫成功**时 +1，而最高境界无劫可渡。
- 当前 9/40 层，剩下 31 层只能靠「转生 → 重新爬境界」循环刷。这是有意设计还是遗留，需要明确。

### 3. 缺少长期目标载体
- 没有成就 / 图鉴 / 统计页 / 赛季之类的东西。到顶之后玩家没有可收集、可比较的对象。
- 商品 288 种、股票 100 只、行业 48 个已经铺满，融合赛道（v3.6）在后期也没有新的解锁或挑战。

## 三、值得优化

### P0 · 性能：离线结算单次 6.7 秒同步阻塞

实测（`/api/load`，真实 HTTP，48 小时离线、153 台产线、288 商品）：

```
48 小时离线后首次 /api/load : 6741 ms
紧接着第二次                :   18 ms   ← 基线，说明全部开销都在离线结算
```

原因有两层：

1. **逐台循环 × 自适应步数**。`syncCompany` / `companyOutputPerCycle` 按「线 × 台」遍历，
   而离线步数固定约 600 步（步长 `max(60, 总时长/600)`）。于是工作量 ≈ `台数 × 600`。
   18 台时 48 小时是 381 ms，153 台时变成 3428 ms —— **近似线性**。
2. **同一笔离线被算了两次**。`/api/load` 先 `previewOffline()`（内部 `hydrate(serialize(s))` 复制一份状态、
   跑完整 tick、再 `stockSummary`），拿到「离线收益弹窗」的汇总；紧接着又对真实状态 `tick()` 一遍。
   两份开销完全重复。

建议（按性价比排序）：
- `tick` 在离线结算时把公司/市场/股市的统计顺带累计出来，`previewOffline` 直接复用，**先砍掉一半**。
- `syncCompany` 里对同一产线的多台做批量聚合（同产物同产能的台合并成一次计算），而不是逐台。
- `syncMarket` / `syncStocks` 加「没跨期就早退」（周期只有 60 / 600 两种，跨期判定很便宜）。
- 再不够就把离线结算分片（按游戏内月份切开，`setImmediate` 让出事件循环），避免整台服务停摆。

### P1 · 数值：「工业产能」投向与「优先生产」在后期彻底失效

```
工业算力池 9.60e22　需求 2.43e14　供需比 3.95e8
分档 pri / norm / scale = 1 / 1 / 1
```

- 算力池 = `实际算力 × 工业份额 × ratio(固定 1)`。需求 = `Σ maxCompute × 产能`，只随**台数线性**增长；
  而实际算力被设备（指数）和 AI 投向（逐 tick 累加、**无上限**）推到 1e23 量级。两者差 8 个数量级。
- 后果：后期把「工业产能」份额从 20% 调到 1% 依然满负荷；「优先生产」标记完全不影响产量。
  也就是说这两个机制只在**前中期**有意义。
- 而实际算力 4.8e23 里，有效设备算力只有 7.2e19 —— **6000 余倍的差距来自 AI 投向的逐 tick 累加**。
  这正是 `doRebirth` 注释里提过的「转生刹车失灵」的同一个源头。

建议：
- 给 AI 投向的累加吃一个软上限（例如按 `sqrt` 或 `log` 衰减），或让它随境界设上限。
- 让 `industrialCompute.ratio` 随境界缩放，或者把产线的 `maxCompute` 改成随境界增长，
  否则「工业算力」这个约束在元婴之后就不存在了。

### P1 · 体验：算力充足时「优先生产」没有任何反馈（**已修**）

本轮顺手修掉了：算力充足且存在优先标记时，状态行改成
「算力充足 · 满负荷　（已标记 N 条优先线；当前算力不缺，暂不影响产量）」。
一个能点但看不出作用的开关，比没有这个开关更糟。

### P1 · 体验：顶栏「实际算力」数字对不上账（**已修**）

旧代码副行写的是 `总设备算力 + AI`：既没扣兵解衰减，也没乘神识 / 被动乘区。
后期这两项合计才 `1.01e20`，而标题写着 `2.27e23` —— **差约 2000 倍**，玩家只会以为算力算错了。

改为统一走 `Core.computeBreakdown(s)`，返回 `{ device, ai, mul, base, total }`，
且 `total` 与 `realComputeOf(s)` 严格相等；副行显示 `设备 … + AI …　乘区 ×…`。

```
设备 7.22e19 + AI 2.88e19　乘区 ×2,247
(7.22e19 + 2.88e19) × 2247 = 2.269e23     标题 = 2.27e23      偏差 0.02%
```

同时修掉投向面板 `techexp` 提示里的一个同类问题：它把无上限的原始数值直接吐给玩家看。

### P2 · 测试脚手架：29 条断言长期恒真、形同虚设（**已修**）

`tests/core.test.js` 里 `ok()` 的签名是 `ok(条件, 名称, extra)`，但 v3.x 后期新增的若干块
写成了 `ok(名称, 条件, extra)` —— **同一个文件混了两套参数顺序**。

后果很隐蔽：条件位置被传了字符串（恒真），名称位置被传了布尔，输出全变成 `✓ true`，
于是这 29 条断言**从来没有真正校验过任何东西**，还照样计入「通过」。
归一化 `ok()` 之后立刻暴露出其中一条真失败：

```
✗ 除天级外每个稀有度至少 1 本境界解锁  -> 荒:0 洪:1 宙:1 宇:1 黄:1 玄:1 地:1
```

追下去是断言自己的计数 bug：荒档那本境界解锁功法的 `realm` 就是 `0`（凡人档），
而它用的是 `if (t.realm)` 真值判定，把 `0` 当成「没写」。数据本身是齐的
（每档稀有度各一本，解锁境界恰好等于该档档位 0…7），改成 `t.realm != null` 后通过。

处理方式：`ok()` 按参数类型自动归一（名称必为字符串、条件必非字符串），两种写法都对，
以后新写也不会再踩。**注意这条教训是通用的：测试通过数不等于测试有效数。**

### P2 · 前端：市场页有掉帧

真机帧间隔采样（80 帧，`sama05_co` 后期存档）：

| 页面 | 平均帧间隔 | P95 | 最长 |
|---|---|---|---|
| 境界页 | 8.19 ms | 16.3 ms | 22.6 ms |
| 公司页 | 8.70 ms | 24.0 ms | 29.6 ms |
| 市场页 | 12.66 ms | **58.1 ms** | 76.1 ms |
| 股市页 | 8.42 ms | 25.4 ms | 31.0 ms |

- 市场页最重（288 商品行 + 48 行业组 + 行业景气列表 + 迷你走势图）。
- 全站 **16,200 个 DOM 节点**，页面切换只是显隐，节点全部常驻。
- 值得做：商品行改为虚拟滚动 / 分片渲染；迷你走势图延迟到可见时再画；
  隐藏页停止每帧回填（现在 `renderAll` 会刷新所有页）。

### P2 · 状态不跨刷新持久化

- 商品排序（字段 / 升降序）与产业折叠状态都只存在内存里，刷新后回到「按行业分组 + 融合行业默认折叠」。
  需求只要求「数据刷新后保持一致」（已满足），但跨刷新记住会明显更顺手 —— 一个 `localStorage` 键的事。

### P2 · 存档写入

- 存档 39.8 KB，前端每 15 秒全量 `JSON.stringify` 写一次。目前完全够用，
  但如果后面内容继续涨（商品 / 股票再翻倍），可以改成只写变更或拉长间隔。
- `data/game.db-wal` 已经在上一轮修好（启动 `wal_checkpoint(TRUNCATE)` + `wal_autocheckpoint=512`，
  5.5 MB → 16 KB），这里不用再动。

### P3 · 遗留的数值校准项（README「校准观察」）

- **「太虚晶格超算」灵石门槛**：README 记的是「贪婪买法跑满 168 小时也买不到」。
  本轮推进脚本直接给了灵石，**没有在自然玩法下复验过**，这条保留待验。
- **渡劫基础成功率**已预留到第 8 阶（`baseRate: [0.96 … 0.5]`），在高境界配合
  算力冗余 / 功法 / 道行加成后实测落在 `maxRate = 0.95` 附近；由于 roll 是状态的确定性散列，
  「一次失败 = 被动兵解、境界归零」的代价在最高境界依然很重，可以再评估是否要给一次保底。

## 四、验证方法附记

- 内核：`npm test` —— **4053 项全绿**（Decimal 87 / 核心 2944 / 前端 529 / 端到端 493），
  `tools/sanity-core.js` 203 项全过。

  用于观察后期盘面；离线耗时用真实 HTTP `/api/load` 计时（见 P0）。
- 新增的常驻回归断言（防止这类问题复发）：
  - `tests/core.test.js`：`ok()` 归一化后重跑的「顶栏算力拆解」块，钉死
    `base = 设备 + AI`、`total = base × 乘区`、`total === realComputeOf`、tick 一致、存档往返一致。

    （会拿到 Promise 静默失败），并断言 `registerSync / loginSync` 与异步版行为一致。
  - `tools/verify-v38.py` 第四段：把顶栏副行文本反解成数值，断言
    `(设备 + AI) × 乘区 ≈ 标题`（容差 6%，真机实测 0.02%）——防止再有人只取其中一截去显示。
- 可用工具（都在 `tools/`，已写进 README 目录）：
  - `node tools/advance-account.js <用户名> [--realm N] [--hours H]` —— 把账号推进到指定境界 / 产业规模。
