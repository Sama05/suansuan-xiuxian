# 算力修仙

放置类数值游戏。以算力入道，以设备筑基。

## 快速开始

```bash
npm install
npm start          # 启动服务，默认 http://localhost:3210
```

> 需要 Node ≥ 18（`better-sqlite3` 是原生模块，首次安装会编译，Windows 上可能需要 VS Build Tools）。

浏览器打开 `http://localhost:3210`，注册账号即可开玩。

```bash
npm test           # 运行全部测试（4053 项）
```

> 想在测试里跑端到端用例，需先 `npm start` 另开一个终端。未启动时该套件会自动跳过。

## 玩法

八个子页面，从顶栏切换：

| 页面 | 内容 |
|------|------|
| **境界** | 当前境界、突破进度、时间速率档位、神识与灵气产出倍率 |
| **工作** | 精力条 + 当前工作 + 工作列表（前期主要的赚钱手段） |
| **设备** | 购买算力设备；后 5 台是「修仙 × 科技」，双造价（金钱 + 灵石）并增幅神识 |
| **投向** | 把算力分配到六条路线（修仙 / AI / 计算设备 / 金融 / 功法算力 / 工业产能）；底部预设按钮的份数随**已解锁方向数**变化 |
| **功法** | 未习得前为锁定占位；习得后显示当前修炼、熟练度、功法阁、常驻被动、神识面板 |
| **公司** | 未注册前为锁定占位；注册后显示经营概览、仓库、工业算力、生产线（每个产业组头可**一键满速 / 一键停工**批量改产能；每条线可开**优先生产**，算力不足时优先保障；每台可换产物 / 调产能） |
| **市场** | 独立页面；默认按行业分组展示 288 种商品的行情、走势、抛压与库存操作，顶部四个**互斥排序**（价格 / 涨幅 / 跌幅 / 行业）可切平铺榜与分组视图（未成立公司也能看价） |
| **股市** | 未开户前为锁定占位；开户后显示账户概览、行情时钟、市值前 10 榜单（可展开全部 100 家）与买卖 |

核心循环：

```
工作（消耗精力）→ 金钱 / 灵气 / 灵石
     ↳ 买算力设备 → 算力 → 分配到 修仙 / AI / 计算设备 / 金融 / 功法增幅
     ↳ 买下第一台个人电脑 → 获得第一本功法 → 解锁 功法 / 神识 / 灵气 三个系统
     ↳ 修炼功法（涨熟练度）→ 灵气吸收速度 ↑  → 灵气 → 突破境界
     ↳ 境界提升 → 更快的时间档位 + 更高的精力上限 + 更高阶工作 + 更高基础神识
     ↳ 注册公司（炼气 + 5 万）→ 买生产线 → 拨工业算力 → 每台线选产物/调产能 → 每 20 秒一个生产周期
          → 产物入库 → 按市价卖出 → 金钱（不消耗精力，但与时间档位无关）
     ↳ 开户（炼气）→ 买卖五只股票 → 赌自然价方向赚差价，但自己的买卖会反压成交价
```

### 两种货币 + 两个属性

改数值前务必分清这四个东西，`game-config.js` 顶部也重复了一遍：

| 名称 | 定位 |
|------|------|
| **金钱** money | 买算力设备。来源：工作 + 设备被动收益 + 投向「金融行业」 |
| **灵气** qi | **突破境界的唯一货币**。必须先习得功法才会产生 |
| **灵石** spiritStone | **后期修仙类资源**，用于购买「修仙 × 科技」设备（金钱 + 灵石双造价） |
| **算力** compute | 设备提供，投向五个方向 |
| **神识** shenshi | 一开始就有，随境界成长、被设备增幅。**同时**放大「实际算力的效果」与「功法修炼速度（= 灵气提升速度）」 |

> 早期版本把「灵石」同时当作突破资源。v2 拆分：突破资源改名为**灵气**，灵石独立为后期购买力。旧存档读取时会自动把旧的 `spiritStone` 迁移到 `qi`。

### 时间系统

所有玩家都从 **2000 年** 起步。游戏内时间按「速率档位」推进，档位越高，同样的现实时间在游戏里走得更远，工作完成得越快：

| 档位 | 名称 | 速率 | 解锁境界 |
|------|------|------|----------|
| 1 | 缓 | 1 秒 = 10 分钟 | 凡人 |
| 2 | 常 | 1 秒 = 1 小时 | 炼气 |
| 3 | 疾 | 1 秒 = 1 天 | 筑基 |
| 4 | 倏 | 1 秒 = 1 月 | 金丹 |

默认自动跟随已解锁的最高档位；也可以在「境界」页手动锁档。顶栏随时显示游戏内日期。

> 设计意图：**境界越高，光阴越快**。越往后的工作耗时（游戏内时长）越长，但配合更快的档位，玩家感知到「做完一份工作」的现实时间大致恒定（约 10–30 秒）。


**顶栏四键（v3.3）**：时间流速的选择器放在顶栏游戏时间旁 —— `◀` 减速一档 ·
`▶` 常速（1 秒 = 1 小时，点击后变 `⏸` 暂停）· `▶▶` 加速一档 · `▶▶▶` 直接跳到已解锁的最高档。
档位**完全手动**（自动跟随已废弃），具体倍率看时钟旁的数字。
**1 秒 = 1 游戏年**这一档要**化神**（id 5）才解锁 —— 超出元婴再给最高速，
终局循环里反复重爬才不至于每世都耗同样的挂机时间。

**暂停**只停**游戏内时间**（工作进度、日期）；精力恢复、算力投向、公司周期、功法修炼都挂现实时间，照常推进。
### 工作系统

工作全程都是金钱的主要来源。当前收录 15 份基于现实职业的工作，按「解锁境界 + 前置工作完成次数」逐级放开，形成升职感：

```
街头发传单 → 便利店店员 → 外卖骑手 → 网约车司机 → 物流分拣中心
  → 工地塔吊操作员 → 初级程序员 → 注册会计师 → 三甲医院主治医师
    → 律所合伙人 → 上市公司高管 → 创业公司 CEO
      → 灵矿勘探开采工程 → 洞天福地基建工程 → 灵脉算力网络建设
```

前 12 份是纯现实职业；后 3 份是**修仙 × 科技**的融合岗位，会同时产出**金钱 + 灵气 + 灵石**。每一项都严格遵守单调性：层级越高，工作耗时越长、单次精力消耗越大、金钱/小时越高、金钱/精力也越高（不会出现「高级工作更亏」）。

**精力**：上限随境界提升（凡人 100 → 元婴 660）。按**现实时间**每秒 +1 恢复，与现实时间绑定、不受速率档位影响 —— 这是刻意的，精力是产能的硬上限，否则玩家把时间档位拉满就能无限产出。精力不足时工作会停在原地等恢复，**进度不丢失**。

**两种推进方式**：

- **自动**：开启「自动工作」后按循环自动完成当前工作，离线也照常结算
- **手动催工**：点「催工」立即完成一次（快捷键：数字键或空格），消耗同样的精力


**精力恢复速度随境界提升（v3.3）**：`realms[].regen` 从凡人 1 点/秒按 ~×1.45 / 境抬到合体 20 点/秒。
工作的单次精力消耗也在涨（15 → 38 → 80 → 200 → 520），恢复恒为 1 的话元婴期做一份工作要干等 8 分钟。
抬高恢复速度**不会让收入失控**：高档位下工作收益的瓶颈会自动从「精力」切到「游戏时间」
（`advanceWork` 取两者较小值），恢复再快也加不了钱，只是把「干等」变成「接着干」。
### 设备系统

10 台设备，分两类：

**纯科技（5 台，金钱买）**：个人电脑 → 工作站 → 大型集群 → 数据中心 → 超大数据中心集群。
`costGrowth` 逐台变陡（1.10 → 1.18），单台算力跨数量级跃升。

**修仙 × 科技（5 台，金钱 + 灵石双造价）**：

| 设备 | 算力 | 神识增幅/台 | 灵石产出/秒 | 灵石造价 |
|------|------|------------|------------|----------|
| 灵石供电机柜 | 5e8 | +0.5 | 5 | 2e3 |
| 灵脉直连阵列 | 5e10 | +2 | 40 | 5e4 |
| 阵法加速节点 | 5e12 | +8 | 400 | 1.5e6 |
| 洞天算力中心 | 5e14 | +30 | 5,000 | 5e7 |
| 太虚晶格超算 | 5e16 | +120 | 80,000 | 2e9 |

> 用户要求「后期设备对神识的增幅更高，尤其是科技修仙设备」—— 所以后 5 台的 `shenshiBonus` 是数量级跃升（0.5 → 2 → 8 → 30 → 120），并且它们自己能产灵石，让灵石经济可以自我滚动。

### 金钱来源

| 来源 | 定位 |
|------|------|
| 工作 | 前中期主力，跨数量级增长 |
| 设备被动收益 | 后期底盘，稳定但不暴涨（`base.autoIncomePerCompute` 刻意压低） |
| 投向「金融行业」 | 短线变现，换取买设备的本金 |
| **公司卖出商品** | 中后期主力（见「公司系统」）。不消耗精力，但与时间档位无关 |

> 后期金钱消耗会显著变大，单靠工作不够 —— 这正是公司系统存在的意义：它把「金钱」从「拿时间换」变成「拿资本与判断换」。

### 投向路线

五条路线相互强化，不是互相替代：

| 路线 | 作用 | 定位 |
|------|------|------|
| 修仙方向 | 灵气（境界）的核心来源 | 主线 |
| AI 领域 | 产出转化为算力增量，放大所有路线 | 中线 |
| 计算设备领域 | 产出**累积**进议价值，永久压低设备造价（按设备现价稀释，软上限 60%） | 中线，优惠永久保留 |
| 金融行业 | 直接变现，换取买设备的本金 | 短线 |
| 功法算力投入 | 产出换算成**功法经验**，只喂当前修炼的那本（经验速率 = 挂机基础 + 投向） | 需先习得功法 |
| 工业产能 | 把算力拨给生产线，决定全厂产能 | 需先成立公司 |

分配比例之和不超过 100%。**修仙为 0% 且功法增幅为 0% 时灵气不会增长，境界无法推进**。未解锁的「功法增幅 / 工业产能」不参与分配，它们的份额会自动让给修仙。

#### 每条路线的显示口径（重要）

各方向的「产出」量纲不同，界面用 `investOutputRate()` 换算后展示，**不要直接显示 `investOutput`**：

| 路线 | 显示 | 说明 |
|------|------|------|
| 修仙方向 | 灵气 / 现实秒 | **已含灵气倍率**。早先显示的是没乘倍率的裸值，玩家看到的数字比实际小一到两个数量级 |
| AI 领域 | 算力 / 现实秒 | 已乘 `aiToCompute` |
| 金融行业 | 金钱 / 现实秒 | |
| 计算设备领域 | 产出**累积**进议价值，永久压低设备造价（按设备现价稀释，软上限 60%） | 中线，优惠永久保留 |
| 功法算力投入 | 产出换算成**功法经验**，只喂当前修炼的那本（经验速率 = 挂机基础 + 投向） | 需先习得功法 |
| 工业产能 | 工业算力 | 池子规模，不是每秒资源 |

#### 数值（2026-09-23 重平衡）

早先的问题是**量级脱节**：修仙方向 `rate = 0.01`，筑基期（阈值 5e6）拉满也只显示二十几/秒，
静态比（阈值 ÷ 速度）高达几十万秒；AI 的 `aiToCompute = 0.02` 让算力 1e6 时每小时只涨 1.8%。
现在的取值与实测（`node tools/sim.js 12 xiuxian 5` 的「投产出力」表）：

| 参数 | 旧 | 新 | 依据 |
|------|-----|-----|------|
| 修仙 `rate` | 0.01 | **0.25** | 静态比从几十万秒压到 15~33 天（体感每境 20~30 分钟），数字与阈值可读 |
| AI `rate` / `decay` | 0.05 / 0.70 | **0.35 / 0.75** | 与修仙同指数，算力越厚不掉队 |
| AI `aiToCompute` | 0.02 | **0.006** | 全押 1 小时：算力 1e6 时 +88%、1e8 时 +21%（旧值 1.8% / 0.4%） |

> 想整体拖慢 / 加快主线：**一次只动 `investments[].rate` 或 `realms[].need` 之一**。
> 两者同调等于没调（比值不变）；投向调大而阈值不动，主线会明显变快 ——
> 本次重平衡后 `sim.js` 最优操作到元婴约 **1.8 小时**（旧 5.1 小时），
> 换来的是「投向数字可读」+ 渡劫失败的真实代价。

### 功法系统

**获取链**：买下第一台**个人电脑** → 自动习得第一本功法（黄级「九章算经·残卷」）→ **同时解锁功法系统、神识系统、灵气系统**（在此之前灵气恒为 0）。之后每本功法按「境界 + 算力」条件自动习得。

**同一时间只能修炼一本**，可在「功法」页切换。

**命名规则**：数学的深奥程度 × 修仙术语。**功法表按数学深度升序排列，稀有度跟着走** ——
「天字号功法却只讲四则运算」是明确红线，新增功法要插进对应的深度位置。

**规模（v3.4）**：**41 本**，每个稀有度 ≥ 5 本（天级 6 本）。除「天」外，每级至少一本走
**境界解锁**（沿用 realm + 算力门槛）；其余为**行为成就解锁**，稀有度越高条件越苛刻：

| 成就类型 | 条件示例（由易到难） |
|---|---|
| 行为量 | 完成工作 N 次 · 持有设备 N 台 · 仓库扩容至 N 级 |
| 市场线 | 第一次赚到钱 → 累计卖出收入 1e6 / 1e10 / 1e12 / 1e14 |
| 股市线 | 第一次赚到钱 → 累计实现盈亏 1e5 / 1e7 → 成交 N 笔 |
| 操纵市场 | 市场抛压（清仓砸盘的高水位）曾达到 20% → 40% → 55% → 70% |
| 终局线 | 兵解 ≥ 1/2/3 次 · 渡劫淬体 ≥ 3/8 层 |

条件实现为 `cond: { 类型: 参数 }`（如 `{ marketRevenue: 1e10 }`），由核心层
`techUnlockConditionMet` 判定 —— 全部是状态读数，无随机，前后端各跑一份结果一致。
`peakPressure`（历史最高抛压）为只增字段，服务端 /api/save 有对应保护。

所有功法的解锁条件可点「功法阁 → 图鉴」查看：图鉴按稀有度分组展示全部 41 本，
已得的标绿，未得的灰显并附条件原文；功法阁本体只显示已拥有的功法。

完整功法表（41 本）见 `shared/game-config.js` 的 `techniques.list` ——
每本都带门类（数学分支）、稀有度、主属性基值、被动与解锁条件，此处不再逐本罗列。
**主属性通项**（v3.3 起熟练度吃主属性；v3.5 起等级独立）：

```
灵气吸收加成 = 稀有度基值 × (1 + 功法等级 × 0.08) × 熟练系数
熟练系数     = 0.5 + 0.1 × 熟练段位        ← 入门 0.5 → 圆满 1.0
```

**功法等级（v3.5 重做）**：**每本功法独立经验 / 独立等级**，无上限，跨兵解保留。

```
经验速率 = expPerLog10 × log10(1 + 实际算力)     ← 挂机基础，算力越高越快
         + expPerInvest × 功法算力投向产出       ← 投向加成
升级需求 = 30 × 1.35^当前等级
```

经验**只喂当前修炼的那一本** —— 想练哪本就切过去挂机，等级各自独立、
不会因为总算力涨了所有功法一起升。兵解只清熟练度进度，**不清等级** ——
这是转生后能尽快重推境界的主要抓手（转生衰减压设备算力，但功法等级还在）。

没有熟练系数这层的话，段位在「修满拿被动」之前只给一行文字，修炼毫无正反馈。
现在每升一段主属性 +10%，**满熟练度时功法全属性最强**（主属性拉满 + 被动常驻）。

```
灵气吸收加成 = 稀有度基值 × (1 + 等级 × 0.08) × 熟练系数
熟练系数     = 0.5 + 0.1 × 熟练段位        ← 入门 0.5 → 圆满 1.0
```

没有熟练系数这层的话，段位在「修满拿被动」之前只给一行文字，修炼毫无正反馈。
现在每升一段主属性 +10%，**满熟练度时功法全属性最强**（主属性拉满 + 被动常驻）。

**熟练度**：6 段 —— 入门 / 熟练 / 小成 / 精通 / 大成 / 圆满（累计熟练度 0 / 60 / 240 / 900 / 3000 / 9000）。

- **修炼**：挂机自动积累熟练度，速度 = `1 × (1 + 神识 × 0.02)` 点/现实秒
- **参悟**：消耗灵气（当前境界突破需求的 2%），立即获得一笔熟练度（相当于熟练度的「催工」）
- **被动转常驻**：熟练度修满（圆满）后该功法的**被动属性转为常驻**，之后切换到别的功法也不会丢失

> 存档里功法的三件事分开存：`mastery`（进度）/ `tier`（段位）/ `passive`（被动是否常驻）。兵解（见「待建设」）要用到这三者的差异：**保留功法、清空等级、清空熟练度进度、保留熟练度段位**。

### 神识系统

神识**一开始就有**（凡人基础 1），不属于「习得功法才解锁」的范畴 —— 解锁的是灵气与功法页。它的总量：

```
神识 = 境界基础神识 × 设备倍率 × (1 + 功法被动加成)
      凡人 1 → 炼气 4 → 筑基 14 → 金丹 40 → 元婴 100
      设备倍率 = 1 + Σ(设备.shenshiBonus × 持有数)
```

它同时作用于两处：

- **放大实际算力**：`实际算力 = (设备算力 + AI 加成) × (1 + 神识 × 0.02) × (1 + 功法被动算力加成)`
- **放大功法修炼速度**：`修炼速度 = 1 × (1 + 神识 × 0.02)`，而修炼速度就是灵气提升速度

### 公司系统（产业）

**公司不是「更好的工作」，而是一条独立的经济线。**

| | 工作（职业） | 公司（产业） |
|---|---|---|
| 本质 | 别人雇你，你出卖时间 | 你自己造商品、自己卖 |
| 收益 | 固定（配置死） | 随**市价**浮动 |
| 消耗 | 精力 | 精力外的**维护费**（按所选产物计） |
| 推进 | 游戏内时间（受档位加速） | **现实时间**（20 秒 / 周期，与档位无关） |
| 瓶颈 | 精力上限 | 工业算力 + 仓库容量 + 现金流 + 择时 |
| 尺度 | 单次收益随境界跨数量级暴涨 | 靠**规模**（多买生产线）与**算力配置**取胜 |

关键设计是最后两行：生产周期挂在**现实时间**上，所以把时间档位拉满**不会**让公司多产一分钱。公司要赚得多，只能多买线、并给够工业算力；价格好时手动卖货。

**注册**：炼气期 + 5 万金钱。注册后才有资格买生产线。

**每周期三步**（顺序不能打乱）：

1. **扣维护费**（按当前每台线的产物与产能计费）。钱不够 → 本周期**停产**，但不欠费（不会扣成负数）
2. **各生产线按实际产能产出入库**。仓库满 → 超出部分**直接放弃**，形成经营压力
3. **自动卖出**（可关）。开着就按当前市价清仓

**生产线（12 类，每类 ≥6 种产物）**

新版本把「固定产物」改成「买下一条产线后，**每一台都能自由选择产物与产能**」：

- 每条线有一个固定的**行业**和**算力上限**（如矿井：采掘行业、4000 算力 / 台）
- 一条线能造的全部产物 = 该行业的 6 种商品（如采掘：铁矿石、焦煤、铜矿石、铝土矿、硅石、稀土矿）
- 每台线独立配置：产物下拉 + 产能拖动条（0%–100%）+ 全部套用按钮
- 产量 = 线基准产量 × 产物系数 × 产能 × 算力削减系数
- 维护费 = 所选产物 × 当前价 × upkeep 费率 × 产能

科技线：矿井 → 炼钢厂 / 化工厂 → 精密制造厂 → 电子元件厂 → 整机装配厂。
修仙线：灵田 → 符箓工坊 / 丹房 → 炼器坊 → 阵盘锻造坊 → 洞天营造司。

**工业算力**：

- 买线只拿到「产能上限」，真正转起来要靠**「工业产能」这一投向**
- 工业算力 = 设备总算力 × 你拨给「工业产能」的份额
- 全厂算力需求 = Σ(每条线 maxCompute × 该台产能)
- 供给 < 需求时，**全厂按比例削减**（不是先到先得）；所以多买线不会凭空增产，只会把每条线摊薄
- 界面提供「工业算力」面板：实时显示供给 / 需求 / 削减比例 / 份额，不足时一键跳到「投向」页

**行业与成本传导**：

- 12 个行业组成上下游 DAG：采掘 → 冶炼/化工 → 精密/电子 → 整机；灵植 → 制符/炼丹 → 炼器 → 阵盘 → 洞天；修仙线与部分科技线也互相喂（如炼器需要金属）
- 上游商品价格涨跌会顺着产业链传导：
  - **成本指数** = 上游价格 × `passThrough`（一般 0.5 左右）→ 下游成本涨得快
  - **售价指数** = 上游价格 × `pricePass`（一般 0.25–0.32）→ 下游售价跟涨得慢
  - 结果：上游涨价会压缩下游毛利，玩家能直观看到「矿价涨了，钢厂毛利掉了」
- 行业景气面板把每个行业的「成本指数 / 售价指数 / 上游价格水平」实时列出来

**仓库**：基础 500 件，每级 +600，共 40 级（满级 24500 件）。升级价按 ×1.55 递增。仓库是公司唯一的「软上限」，压货久了就白干。

**市场（确定性价格）**：市价**不用随机数**。**自然价**由 `(商品序号, 期数)` 喂进一个散列函数推导 —— 同一个输入永远得到同一个价格。这一点是硬约束：前端每 100ms tick 一次、后端离线一次性结算 48 小时，两边必须算出**完全相同**的价格，否则「屏幕上看到的钱」和「服务器存的钱」会对不上。实际成交价 = 自然价 × 行业售价指数 × 抛压修正（没有抛压且上游平价时两者相等）。

- 第 0 期 = 开市，直接按配置里的 `basePrice` 挂牌
- **「期」按现实时间计**：科技类 60 秒一期（`periodSeconds: 60`），修仙类 600 秒一期（`periodSeconds: 600`），**与时间档位无关**。早先按「游戏内年」计时，档 4（1 秒 = 1 游戏月）下 1 游戏年只剩 12 现实秒 —— 抛压 4 期就衰减干净，把档位拉满等于免掉砸盘的惩罚（详见下面「市场抛压」）
- 期长与公司生产周期（20 秒）成整数倍，保证一期里恰好跑完整数个生产周期，「本期卖出 / 本期产出」的计数才干净
- 涨跌标记沿用中国习惯：**涨红 / 跌绿**（`.trend.up` → `--red`，`.trend.down` → `--jade`）
- 市场已从公司页**独立成一个页面**，按行业分组展示 288 种商品；未成立公司也能看行情，但卖货需要公司

**价格走势图**：市场页顶部是当前选中商品的走势折线，每个商品行里还有一条迷你走势；点商品行即可把大图切过去。画法与公司页相同：实线已发生 / 虚线推演 / 灰点线基准价，有抛压时叠一条自然价参考线；约束仍是不使用 `<circle>`、描边带 `vector-effect`。

**离线**：公司照常生产（`offline.companyWhileOffline`），但同样按 30% 效率折算、同样受维护费约束，所以不会比在线更赚。

**市场抛压（卖出反噬）**：规则是「**卖超产才会被压价**」：

- 「期」按现实秒计（科技 60 秒 / 修仙 600 秒），**不受时间档位影响**
- 每期分别记账 `soldThisPeriod`（本期货卖出的件数）与 `producedThisPeriod`（本期入库的件数）
- 到了**期数边界**结算一次，抛压增量：
  ```
  超额 = max(0, 卖出/期数 − 产出/期数)
  抛压增量 = 超额 / max(baseVolume, 产出/期数)
  新旧抛压 = 旧抛压 × 0.5^跨越期数 + 增量 × 0.5^(跨越期数−1)（再夹到 [0, 1]）
  ```
  两者是**相加**：连续砸盘会一轮轮叠高，停手之后才按半衰期逐期恢复
- **正常经营（自动卖出 = 产能）→ 超额为 0 → 抛压恒为 0**。只有**囤货砸盘**才会被压价
- 当前期的成交价 = `自然价 × 行业指数 × (1 − 抛压 × maxDrop)`；综合价另有保底倍数 `floor=0.15`（不低于基准价的 15%）
- 结算在 `stepTick` 里排在 `syncCompany` **之前**，保证「本期卖出的货」影响的是**下一期**的价格

前端配套：每个商品行多一条**抛压条**；走势图叠自然价参考线；市场页顶部汇总「抛压最高 X%」。数据侧：`pressure / soldThisPeriod / producedThisPeriod / lastPeriod` 随存档走；`hydrate` 夹范围，`lastPeriod` 夹到不超过当前期；后端 `/api/save` 把 `pressure` 夹到 `[0,1]`。

### 股市系统（证券账户）

**股市不是「无风险的被动收入」，而是一个零和的赌局 —— 唯一稳定的收益来源是「赌对自然价的方向」。**

公司与股市的关系：公司是「自己生产、自己卖」，股市是「买卖别人手上的公司」。股价用**确定性函数**，并额外承受**你自己的持仓冲击**；同时每只股票下面都显示 **主营业务**，行情一动就能看出波及哪些公司。

| | 公司（产业） | 股市（证券） |
|---|---|---|
| 本质 | 造商品、按市价卖 | 赌别人公司的股价波动 |
| 你的作用力 | 卖超产 → 压下一期价 | 买入推高 / 卖出压低**当前成交价** |
| 收益来源 | 产能 × 净收益率 | 自然价的方向（低买高卖） |
| 稳态收益 | 正 | **零和**；随手一轮买卖必亏（溢价 + 双边手续费） |
| 尺度 | 靠规模（多买线）与算力 | 靠本金（后期资金越大，单笔冲击越大） |

**开户**：炼气期。不另收开户费。

**上市公司池：100 家（50 基础 + 50 融合赛道），界面只列市值前 10**

- 30 家科技 + 20 家修仙宗门，每家都有 `business`（主营业务），股市页每行直接显示
- 行情页默认只展示**市值前 10**（`boardSize=10`），榜单随行情换人；点「显示全部 100 家」可展开完整池子
- 交易对全部 100 家开放 —— 接口按 `id` 找，榜外公司照样能买，为后续「收购 / 退市」留玩法

**三层价格**：

```
成交价 = 自然价 × 冲击系数
自然价 = 基准价 × 行情波动因子 × 行业联动因子
```

1. **行情波动因子**：`exp(volatility × k)`，`k = hash01(股票序号, 期数)` 映射到 `[−1, 1]`。**不用随机数**。`volatility` 越大摆动越凶。
2. **行业联动因子**：`1 + (关联商品价格倍数 − 1) × linkWeight`。公司商品属于某个行业，该行业的整体售价指数（含成本传导）会联动到挂钩股票；`linkWeight=0.5` 是刻意的**半联动**。
3. **冲击系数（反作用）**：`1 + 净流入 / 流通盘 × maxRise或maxDrop × (1 + 持仓集中度 × illiquidity)`。买得越多推得越高（`maxRise=0.60`），砸得越狠压得越低（`maxDrop=0.50`）。

**核心机制：成交按「成交之后」的冲击价结算。** 买入的那一瞬间就把价格顶高了，所以成交均价**高于**下单前市价；卖出同理。这就是「一轮买卖必亏」的根源。

- 净买入流**逐期衰减**（`flowDecay=0.5`，一期减半）。你买出来的溢价会随时间消退，**等它涨回去再卖拿不到那个溢价**。
- **持仓集中度放大冲击，但不抬高价格水平**；否则就是无风险套利。
- **手续费双边收**（`fee=0.005`），且设**最小成交额**（`minOrder=1e4`）。
- 成交价另有绝对下限 `floor=0.05`。

**账户概览**：

- **浮动盈亏** = `市值 − 持仓成本（含费）`。市值按当前成交价计 —— 看着好看，但卖不掉。
- **可变现盈亏** = `清仓报价（把你自己的砸盘算进去）− 持仓成本`。点「全部卖出」实际能拿到的钱，通常**明显小于**浮动盈亏。

**结算在 `stepTick` 里排在 `syncCompany` 之后**（第 9c 步，公司抛压结算之后）—— 这样联动因子读到的是**本期已结算完**的商品售价指数。

**前端**：锁定占位页讲清机制；开户后是「证券账户概览 + 行情时钟 + 走势大图 + 行情列表（默认前十，可展开全部）」。每行显示**主营业务**，带冲击条、持仓、浮动盈亏和买卖面板。

**离线**：股市**不在离线结算范围内** —— 它挂在「期数」上，离线期间行情照走，但没有买卖动作。

**数据侧**：`s.stock = { shares, flow, cost, lastPeriod, realized, totalFee, totalTrades }` 随存档走；`hydrate` 逐项夹范围；后端 `/api/save` 对 `shares / flow` 夹范围、`cost` 负值归零，`realized / totalFee / totalTrades` 只增不减。配置见 `game-config.js` 的 `stock` 段。

**性能（2026-09-23）**：股市页曾卡到每帧 300ms+，根因**不在 DOM 也不在图表**，是核心层的两处：
1. `industryPriceRatio` 通过 `goodsPriceWith` **自引用** —— 每层展开「6 件商品 × 上游数」，深度守卫 8 层时展开量是 6^8 量级。修仙下游行业（洞天）单次推导 2.2ms，而 50 只股票每帧各推一次自然价。修法：把行业指数**显式传参**（`industryPriceRatioWith`），递归只沿「本行业 → 上游」的 DAG 向上走。337ms → 31ms。
2. `stockMaxBuy` 的二分查找每次迭代都重算自然价与手续费。修法：`stockBuyQuoteWith` 把不变量提出循环。31ms → **4.7ms**。

前端另加三档：`id → 行` 用 Map（去掉 50×50 的 `find`）、报价按「(期, flow, 持仓, 手数)」缓存（金钱只影响够不够买那一次比较，不进 key）、迷你走势与大图按「(股票, 期, 冲击)」缓存（期内 SVG 是静止的）。

### 渡劫（突破境界的门槛）

**为什么不许「灵气攒够就自动升级」**：阈值是一条纯时间曲线，挂得够久境界必然到手，主线没有赌注。渡劫把它换成「要不要现在过」—— 过了，所有基础加成永久抬一档；不过，这一世作废。

**规则**：

- 灵气满格后**必须渡劫**才能升境；`autoTribulation` 开着时灵气一满就自动闯，关掉则停在「待渡劫」等你手动点（可以先用算力堆成功率）。
- `成功率 = clamp(基础 + 算力冗余 + 功法造诣 + 道行底蕴, 0.05, 0.95)`，四项逐项显示在面板上：

  | 项 | 来源 | 上限 |
  |----|------|------|
  | 境界基础 | `baseRate[境界]`：0.96 / 0.94 / 0.91 / 0.86 / 0.78 / … | — |
  | 算力冗余 | 实际算力每比本境界基准高 10 倍 +3% | +15% |
  | 功法造诣 | 每本修满（被动常驻）的功法 +2% | +10% |
  | 道行底蕴 | 累计道行每 2000 点 +1% | +8% |

- **成功**：境界 +1，**渡劫淬体 +1 层**（永久、跨兵解保留，上限 40 层）。每层：灵气吸收 +6%、实际算力 +5%、工作金钱 +5%、境界基础神识 +4%、精力上限 +4%、灵石产出 +5%。
- **失败**：**被动兵解** —— 走 `doRebirth(s,'passive')` 同一段代码：
  - `realm ≥ 元婴`：等同主动兵解（保留设备 / 功法 / 履历），道行打三折；
  - `realm < 元婴`：**连设备与功法一起清空**（`fullWipe`），只保留工作履历与道行。

**为什么结果必须是确定性的**：前端每 100ms 跑一次 tick，服务端在离线结算里跑同一份 tick —— 结果必须两边一致。所以 `tribulationRoll` 是**状态的纯函数**（散列「境界 / 已尝试次数 / 淬体层数 / 游戏内时间分钟」），不用 `Math.random()`。每次尝试 `attempts` 都 +1，失败后再点得到的是另一个结果，不会卡在必死的那一次。

**为什么浏览器端不本地渡劫**：渡劫失败会清空设备与功法，而这两样在 `/api/save` 里是「只增不减」的 —— 本地先失败再回写，会被服务端原样补回来，变成「界面归零、服务器还留着元婴」。所以浏览器端本地 tick 传 `tribulation:false`，渡劫统一走 `/api/action`（服务端直接落库，绕开那层只增保护）。

**服务端保护**：`/api/save` 对 `tribulation.level / attempts / failures` 只增不减，层数另夹到 `maxLevel`。

### 兵解 · 转生系统（终局循环）

**为什么需要它**：境界表只到元婴，`sim.js` 实测 11.9 小时到元婴，之后进度条恒为 100% —— 主线约 12 小时通关，公司 / 市场 / 股市这些设计量最大的系统全落在「通关之后的沙盒」里，缺一个终局目标。转生把「终点」变成「一轮的终点」。

**触发**：境界 ≥ 元婴，二次确认（弹窗列清「失去 / 保留 / 获得」三栏）。**服务端权威执行**，前端只提交意图。

**道行**：`100 ×(1 + 0.6 × 已兵解次数) ×(主动 1.0 / 被动 0.3)`。

**刻意对资产总量不敏感** —— 否则玩家会先囤到天量资产再兵解，把转生变成一次性的暴富操作，而不是一轮轮的节奏循环。被动入口（`mode: 'passive'`）是给将来的「渡劫失败」预留的：道行打**三折**，失败仍有收益但显著低于主动，否则玩家会故意去渡劫失败刷道行。

**重置清单**（完整清单带理由写在 `game-config.js` 的 `rebirth.wipe` 注释里，新增资源字段时对照它）：

| 归零 | 保留 |
|---|---|
| 境界 · 灵气 · 境界进度 · 灵石 · 金钱（回到起手 20）· 精力 · 投向分配与累计产出 · **aiBonus / investedCompute** · 档位 · 当前工作与进度 · 功法熟练度进度 · 公司全清 · 股市全清 | 功法本体 / 熟练度段位 / 常驻被动 · 设备（吃转生衰减）· **工作履历** · **渡劫淬体层数** · 道行与全部加成 · 游戏内日期与行情时钟（**绝不倒流**） |

**被动兵解（渡劫失败）在元婴之下会额外清掉设备与功法**（`rebirth.passiveExtraWipe` + `tribulation.passiveRules`），只保留工作履历与道行 —— 这就是「未达元婴的被动兵解不保留任何资源」。元婴及以上的失败则等同主动兵解，只是道行三折。

**公司与股市全部清空**（口径由 `rebirth.wipe.company` / `.stock` 控制）：注册状态、生产线、仓库、库存、经营统计；持仓、成本、净买入流、已实现盈亏、手续费与成交笔数。

**转生衰减快照（v3.4）**：衰减只作用于**兵解那一刻的设备存量**（快照存进
`rebirth.baseCompute / baseShenshi`），之后新买的设备按原值全额累加 ——
修掉旧模型「兵解后买设备属性栏几乎不动」的问题（买 5e10 只多出 sqrt 的一半）。
防篡改：快照只在兵解瞬间随 count 一起变化，/api/save 在 count 不变时强制沿用服务端快照。

**设备被动收益也吃转生衰减**（`autoIncome` 走 `deviceComputeEffective`）：早先它直接读原始算力，兵解后 `realCompute` 掉下去了、挂机金钱却还是兵解前的量级，玩家几分钟就能把设备全买回来 —— 主线等于没重来。**凡是由设备算力派生出来的产出，都必须吃同一份衰减。**

#### 转生衰减 —— 整个系统最关键的一处，踩过三个坑

```
指数 f(0 次)  = 1.00                                 ← 没兵解过，原值
指数 f(n ≥ 1) = min(base + perRun ×(n − 1), cap)      // 0.50 → 每世 +0.03 → 0.75 封顶
有效设备算力  = min(原值 ^ f, 上限(n))                 // 上限 = 1e8 × 10^(0.5 ×(n−1))
有效神识倍率  = (倍率 − 1) ^ f + 1                     ← 不夹上限
```

1. **不能用「乘一个比例」。** 第一版是线性折扣 0.35，实测一个元婴玩家兵解后 **0.1 秒内就重新突破回元婴** —— 因为 5×10^17 × 0.35 仍比突破元婴所需的算力高 6 个数量级。**线性折扣对跨 16 个数量级的算力没有刹车力。**
2. **光有幂衰减还不够。** 改成开方之后仍然 **2 秒回元婴** —— 开方只削相对倍数，「前世设备越多、绝对值越高」这件事没被处理。所以再加一道**绝对上限**：不管前世多强，这一世都从同一水平线开始（第 1 世 1e8 → 第 5 世 1e10 → 第 10 世 3e12）。**「越转越快」体现在上限放宽上，而不是靠放宽衰减指数。**
3. **`aiBonus` 必须一起清。** 它是「AI 领域」逐 tick 累积出来的算力增量，性质上属于「这一世攒下的产能」，与设备存量无关。不清它，`realCompute = 衰减后的设备算力 + 巨额 aiBonus`，照样秒回元婴。

> **实测节奏**（真 Chromium）：兵解 → 凡人 → 筑基（瞬间）→ 金丹（约 5 秒）→ 元婴（数十秒到数分钟），对照第一世的 12 小时。所有旋钮都在 `game-config.js` 的 `rebirth` 段，改完可用 `sanity-core.js` 的折扣序列断言快速自检。

#### 存档与防作弊

`s.rebirth = { count, dao, daoTotal, perks, history }` 随存档走。

- `hydrate` 逐项夹取：`perks` 每项夹到 `[0, maxLevel]`（防手改存档把加成填到天上），`dao` 夹到 `[0, daoTotal]`
- `/api/save` 的只增保护：`count` / `daoTotal` / `perks.*` 只增不减
- **单独一道 409**：`/api/save` 若发现 `prevState.rebirth.count > incoming.rebirth.count`，说明客户端手里是**兵解前**的旧存档（典型场景：另一个标签页还在定时回写）。直接拒收并回传服务端版本 —— 否则下面「公司 founded 只增 / 生产线台数只增」会把兵解清空的资产又补回来。

#### 界面上的一个坑

境界页底部的「兵解 · 转生」面板，**显示条件与兵解门槛是两件事**：
`unlocked`（境界 ≥ 元婴）决定**能不能点兵解**；`visible`（`unlocked || count > 0`）决定**面板是否展开**。
兵解后境界会掉回凡人，如果面板跟着锁上，玩家既看不到自己的道行、也花不掉它 —— 这个坑同样是实测出来的（前端 `ui-rb-count` 一直显示 0）。

### 校准观察（留给下一轮调优）

跑 `sim.js` 发现的三件事，都属于「需要更多内容才能定」的问题，先记下来：

1. **各流派收敛**：`even`（均衡）与 `xiuxian`（全压灵气）到元婴的时间几乎一致（1.86h vs 1.83h）。说明真正的瓶颈是**算力/金钱**而不是分配比例 —— 符合设计意图（动态调配优于一路走到底）。想让后期更有减速感，应调 `realms[].need` 而不是调投向。
2. **神识自激回路已加阻尼**：分层口径（境界线性 + 设备对数）已上线，但**渡劫淬体的「实际算力 +5%/层」是新的乘区**，40 层封顶 = ×7。层数是永久资产，等未来加境界（化神 / 炼虚 / 合体）时需要复核它与新阈值的配比 —— `tribulation.baseRate` 已经预留到第 8 个境界。
3. **最后一台修仙设备够不到**：「太虚晶格超算」需 2e9 灵石，而玩家在买前面的「洞天算力中心」（5e7 起、×1.26 递增）时会把灵石池持续抽干 —— 贪婪买法跑满 168 小时也买不到它。要么给灵石开新来源，要么调整后两台的灵石造价阶梯。

## 技术选型说明

### 大数方案：十进制浮点

放置类游戏后期数值会突破 JS `Number` 的 1.8e308 上限，`BigInt` 又无法表示小数。因此自建十进制浮点数：

```
value = sign × mantissa × 10^exponent
mantissa 归一化到 [1, 10)，清洗到 14 位有效数字
```

与 Antimatter Dimensions、Cookie Clicker 等成熟作品采用同一思路，上限约 1e(9e15)，远超游戏需求。溢出时饱和而不是归零。

> 清洗位比 JS `double` 的可靠精度（约 15 位）**低一位**是有意的。按 15 位清洗会把最后一位的浮点噪声当成有效数字留下 —— 例如 `new D(480).add(new D(240))` 会得到 `7.199999999999999e2` 而不是 `7.2e2`（因为 `4.8 + 2.4` 在二进制下不精确）。这类「整数相加得到非整数」的脏值会让 `eq` 比较失效，存档里也会出现长尾巴。留 1 位保护位即可抹掉噪声，而 14 位有效数字对放置类游戏绰绰有余。

### 四条时间线

`tick()` 内部同时维护四条互不干扰的计时：

| 时间线 | 驱动方式 | 作用 |
|--------|----------|------|
| 游戏内时间 `gameSeconds` | 速率档位（1 秒 = 10 分钟 ~ 1 月） | 推进工作进度、顶栏日期 |
| 现实秒累计 `playTime` | 真实经过的秒数（含离线） | **行情时钟** —— 商品市场与股市的「期」都按它推进（`marketClock`） |
| 现实时间 `dt` | 真实经过的秒数 | 设备被动收益、算力投向产出、灵石产出、修炼、精力恢复、**公司生产周期** |
| 精力 | 现实时间，固定 +1/s | 产能硬上限，与档位解耦 |

`stepTick()` 的固定顺序（改逻辑时不要打乱）：游戏时间 → 精力 → 神识/实际算力 → **功法习得检查** → 工作结算 → 设备被动收益 → 灵石产出 → 投向产出 → **市场抛压结算** → **公司周期** → **股市结算** → 修炼涨熟练度 → 硬件折扣 → 境界突破（消耗灵气）→ 自动档位。

> 「功法习得检查」放在工作结算之前很关键：买到个人电脑的那一瞬间，本段 tick 就应该已经能产灵气，而不是等下一段。

> 「公司周期」跟精力一样挂在现实时间上，所以它是一条**与档位解耦的产能上限**：拉满档位只会让工作更强，不会让公司多产一分钱。

> 「市场抛压」必须排在「公司周期」**之前**：跨越期边界时先把上一期的净抛售兑换成本期压力，公司这一段的产出与自动卖出才会用到新价格。而「股市结算」排在公司**之后**，这样联动因子读到的才是同一段里**已结算完**的商品售价指数。

> 行情也挂在现实时间上，是同一个道理：档位只该加速工作，不该加速行情。否则拉满档位就能让抛压与股市冲击瞬间衰减，「砸盘被压价 / 大单砸自己」这两条约束会直接失效。改动前必须知道：`marketClock(s)` 是唯一的行情时钟入口，任何行情函数都从它取时间。

### 顶栏为什么不抖

顶栏资源条最早是 `flex: 1` + `flex-wrap: wrap`，结果出现了「资源条来回跳动 / 自己折叠」——根因是**每个 `.res` 的宽度由内容撑开**：副标题每 100ms 就会在「设备提供」和「设备 1.2万 + AI 3千」之间变长变短，宽度一抖就可能跨过 flex 的换行阈值，整组折到第二行，顶栏变高，下面所有内容跟着上下跳一次。

改法是让列宽**与内容完全无关**：

```css
.res-group {
  display: grid;                                  /* 不再用 flex + wrap */
  grid-template-columns: repeat(6, minmax(0, 1fr));
}
```

grid 的列宽只由容器宽度决定，数值再长再短都不会重排；窄屏用媒体查询把列数降到 3 / 2，但仍是**固定列数**。配套还有三处细节：

- `.res .k / .v / .sub` 单行截断（`nowrap` + `ellipsis`），内容再长也撑不宽所在列；`.sub` 给 `min-height`，避免空文本时顶栏塌一格
- 数值统一 `font-variant-numeric: tabular-nums`（等宽数字）；时钟和用户名限宽，日期位数变化（9月9日 → 10月10日）不再左右推挤
- 渲染层加了 `setText(id, value)` 值缓存：**文本没变就不碰 DOM**。`renderTop` 每 100ms 跑一次，无条件重写 `textContent` 会让浏览器反复做「replace data → 重新测量文本宽度 → 重排」

`tests/frontend.test.js` 的「顶栏布局稳定性」小节把这些都钉住了，包括一条反向断言：`.res-group` 里**不允许再出现 `flex-wrap`**。

### 折叠 / 展开：一处实现，声明式挂载

页面上所有「点一下收起、再点一下展开」的地方共用 `public/js/app.js` 里的 `slideToggle()` + `bindCollapse()`。**新增折叠点只需两步**：

1. 给可点击的标题加 `data-collapse`（值是要展开的元素选择器，写 `next` 取下一个兄弟元素）；
2. 容器上调一次 `bindCollapse(容器, { onToggle })`。

动画是高度过渡（`.col-anim` 临时接管 display + `transition: height .2s`），箭头用 CSS `transform: rotate(-90deg)` 表示方向 —— 不换字符、不在 JS 里改文本。折叠状态写在祖先的 `.folded` 类上，**静止态由 CSS 决定、动画态由 JS 决定**，所以不会出现「收起动画还没播完就被 `display:none` 抹掉」。

> 历史坑：v3.6 的折叠是「改 `folded` 集合 → 整段重建 DOM」。重建出来的 `[data-role="lunits"]` 是空盒子，而台数没变、`unitSigCache` 里的旧签名也没变，于是「签名没变 → 不重建」，每一台的配置行就一直不回填 —— 玩家改了产物看不见，非得再买一条线才冒出来。现在折叠**不重建 DOM**，且重建签名写在元素自己的 `data-usig` 上（元素换了必然重建）。`tests/frontend.test.js` 里有一条反向断言钉住这点。

### 前后端同一份 tick

`shared/game-core.js` 的 `tick()` 同时被前端（100ms 实时刷新）和后端（离线结算）调用。两端算法完全一致，因此不会出现「屏幕上显示的进度」与「服务器保存的进度」对不上。

在线 tick 按 ≤60 秒一段推进（`STEP_REAL_SECONDS`），避免一次性大步长导致的工作进度 / 精力判定失真。

**离线结算的步长是自适应**的：总步数压在 `OFFLINE_MAX_STEPS`（600）以内，即 `步长 = max(60, 总时长 / 600)`。短时离线（< 10 小时）步长仍是 60 秒、结果与在线完全一致；48 小时离线从 2880 步降到 576 步，耗时约降 4 成。之所以能放大步长：所有按周期结算的模块都支持一次跨多期 —— `syncCompany` 内部 while 循环把这一大步里的每个周期都结算掉，`syncMarket` / `syncStocks` 用 `n = 当前期 − 上次结算期` 一次补齐 n 期的衰减；工作 / 精力 / 灵气都是速率 × dt 的线性累积。

### 服务端权威

`/api/action` 走服务端校验：`setJob` / `setWorking` / `rushJob` / `setTimeTier` / `setAutoTier` / `buyDevice` / `setAllocation` / `setTechnique` / `setCultivating` / `comprehend` / `foundCompany` / `buyLine` / `upgradeWarehouse` / `sellGoods` / `setAutoSell` / `buyStock` / `sellStock` / **`rebirth`** / **`buyPerk`** / **`tribulation`** / **`setAutoTribulation`**。

> 渡劫必须走这里（而不是客户端本地 tick）：失败会清空设备与功法，而这两样在 `/api/save` 里是「只增不减」的，本地先失败再回写会被服务端原样补回来。详见「渡劫」一节。

> `rebirth` 与 `buyPerk` 尤其不能放给客户端：道行收益、重置清单、转生衰减、加成等级上限全部由服务端重算，客户端只提交「确认兵解 / 要买哪一项加成」这个意图（与 `buyStock` 的服务端报价同一套纪律）。

其中 `buyStock` / `sellStock` 一律**服务端按自己的报价成交** —— 客户端只提交 `stockId` 与股数，成交均价、手续费、冲击系数全部由服务端重算，返回 `unitPrice / gross / fee / net / impact / sharesAfter` 供前端对账。

`/api/save` 做防作弊，以下字段每个 key **只允许增加**，不允许回退：

```
playTime · realm · gameSeconds · totalJobs · rushCount · jobDone[各工作] · devices
learned[各功法].mastery / .tier / .passive   ← 功法进度同样只增不减
company.founded / .foundedDay / .warehouseLevel / .cycles
company.lines[各生产线] · company.goodsSold[各商品]
company.totalRevenue · company.totalUpkeep
stock.realized / .totalFee / .totalTrades   ← 股市盈亏与成交笔数同样只增不减
rebirth.count / .daoTotal / .perks[各加成]   ← 兵解次数、累计道行与加成等级同样只增不减
                                               （dao 会因消费而减少，所以只夹到 [0, daoTotal]）
```

> **`/api/save` 还有一道 409**：若 `prevState.rebirth.count > incoming.rebirth.count`，
> 说明客户端手里是兵解**之前**的旧存档，服务端直接拒收并回传最新存档。
> 不加这一道，「公司 founded 只增 / 生产线台数只增」会把兵解清空的资产原样补回来。

另外 `learned` 里的键**不允许被整条删除**（清空即拒绝），`technique` 也不允许被清空 —— 否则客户端可以把功法「退掉」再重新触发一次获取。

公司还有一条专门的单向门：**`founded` 只能由服务端点亮**。客户端提交 `founded: true` 但服务端记录里从没成立过 → 直接改回 `false`（否则等于零成本开公司）。

和金钱、设备数量同一档的字段（`money` / `company.stock` / `stock.shares`）**不做只增保护** —— 它们本来就会在卖出与消费时减少。库存的替代约束是**容量上限**（`hydrate` 把超容库存裁到当前仓库容量内）；股市持仓的替代约束是**流通盘上限**（`shares / flow` 各自夹到 `[−流通盘, 流通盘]`）。

客户端只负责展示与实时手感。

### 登录状态（免重复登录）

token **落盘在 SQLite 的 `sessions` 表**，有效期 60 天，使用中自动续期（续期写库节流到 1 小时一次，避免每 15 秒一次的自动保存都打一条 UPDATE）。服务端重启**不影响**已登录的浏览器。

在此之前 token 存在内存 `Map` 里，重启一次全部作废 —— 前端 `localStorage` 明明存着 token，还是被迫重新登录。启动时会顺手清理过期会话，并在控制台打印当前会话数。

> 前端只把 token 与用户名写进 `localStorage`，**不存游戏状态**；状态始终以服务端存档为准。

## 离线收益

- 离开 < 60 秒：视为「短暂离开」（刷新页面、切标签页），**全额结算**，不打折
- 离开 ≥ 60 秒：按 **30% 效率**折算，最多累计 **48 小时**
- 离线期间**工作照常推进**、**功法照常修炼**、**公司照常生产**（`offline.workWhileOffline` / `cultivateWhileOffline` / `companyWhileOffline`），但精力按现实时间恢复、公司按现实时间走生产周期，因此离线产出同样受精力上限与维护费约束
- **股市不参与离线结算**：它靠买卖动作产生盈亏，人不在场就既没有成交也没有冲击。离线期间行情照走（确定性能算出来），但你的持仓价值变化不落进离线收益汇总

阈值与比例都在 `shared/game-config.js` 的 `offline` 段。
